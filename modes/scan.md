# Scan Mode

Scan configured portals for new job postings matching the user's target roles.

## Sources (adapter registry)

All ATS types are handled through the adapter pattern in `scripts/scan.mjs`:

1. **Greenhouse** — `boards-api.greenhouse.io` JSON API
2. **Ashby** — `api.ashbyhq.com` REST API
3. **Lever** — `api.lever.co` JSON API
4. **BambooHR** — `{company}.bamboohr.com/careers/list`
5. **Teamtailor** — native RSS at `{company}.teamtailor.com/jobs.rss`
6. **iCIMS** — Phenom/careers.X.com API (paginated GET) or legacy `{slug}.icims.com`
7. **Workday** — JSON POST to `myworkdayjobs.com` endpoint
8. **RSS feeds** — WeWorkRemotely, HN Jobs, rss.app proxies
9. **localfeed** — file-based adapter reading `data/feeds/{source}.json`

## Cache check

Always the first step for `scan`:

Run `node scripts/read-cache.mjs` (single call). Returns JSON with `{ fresh, ageHours, total, excluded, postings[] }`.

- If `fresh: true` → cached run. Show "Loading your last scan..." then proceed to the pick list using `postings`.
- If `fresh: false` → fresh run. Run `node scripts/discover.mjs --add all` (show "Discovering companies..."), then `node scripts/scan.mjs` (show "Scanning portals..."), then run `node scripts/read-cache.mjs` again to get the updated postings.

Flags:
- `--force` → Skip cache check. Run discover then scan, then read-cache.mjs.
- `--dry-run` → Run `discover --dry-run` then `scan --dry-run`. Preview only, no interactive flow.
- `--source <type>` → Skip discover, scan only one ATS type. Always fetches fresh.

**UX rules:** Do NOT narrate which bash commands are running. Do NOT echo raw script output. Show only human-readable progress. After scripts finish, go directly to the post-scan pick list. No summaries, no script headers.

**OUTPUT RULE (non-negotiable):** Between outputting "Loading your last scan..." and outputting "Best matches from this scan:", output zero lines of text. No cache status, no session status, no match confirmation, no explanatory text.

## localfeed handling

`scan.mjs` reads `data/feeds/indeed.json` and `data/feeds/linkedin.json` when localfeed entries are present in `portals.yml`. These files are generated by a separate Playwright scraper and are NOT created automatically during a scan.

**If localfeed files are missing:**
- Do NOT run `node scripts/generate-feeds.mjs`. Do not attempt to generate them.
- `scan.mjs` will warn and return 0 jobs from those sources — this is expected behavior.
- Show no message about missing feed files. Proceed silently.

## Post-scan interactive flow

After `node scripts/read-cache.mjs` returns (or fresh scan completes), do NOT dump a summary. Use the `postings` array from the JSON output directly.

### Step 1 — Posting pool

The posting pool is already filtered and sorted by `read-cache.mjs`: compatible only (no `compatible: false`), tracker-matched and snoozed postings removed, sorted by relevance desc, top 150 returned. The JSON includes:
- `excluded` — total filtered (incompatible + already tracked + snoozed)
- `excludedTracked` — count filtered because they're in tracker.md
- `excludedDismissed` — count filtered because they were snoozed (dismissed.json)

These counts are internal metrics — do not show them to the user.

### Step 2 — Session pick list check

Read `data/session-pick-list.json` (if it exists). If it exists:
- Compare its `cache_timestamp` field to the `scanTimestamp` from the current `read-cache.mjs` output.
- If they **don't match** (cache was refreshed) → ignore the session file. Proceed with step 3 to rebuild tiers. The new session file will be written after tiering.
- If they **match** → reconcile `shown` against the current postings pool:
  1. Build a Set of valid URLs from the `postings[]` array returned by `read-cache.mjs`.
  2. Partition `shown` into `keep` (URL is in the valid set) and `stale` (URL is no longer valid — tracked or dismissed since the session file was written).
  3. For each stale entry, pull a replacement from the tier buffer matching that entry's `tier` field (same cascade as slot replacement: t1 → t1 → t2 → t3; t2 → t2 → t3; t3 → t3 only; local → local only, no cascade). If all buffers are empty, skip.
  4. Renumber all entries in `shown` (keep + replacements) consecutively starting at 1. Replacements go at the bottom.
  5. Write the updated `data/session-pick-list.json`.
  6. Proceed to step 4 with the reconciled `shown`.

If the session file doesn't exist, proceed with step 3 normally.

### Step 3 — Tier compatible postings

First, derive the candidate's seniority level from their resume:

**Step A — Read `resume.md`** and identify:
- The **current role title** (most recent position)
- The **career trajectory** — management track, IC track, or mixed/hybrid path

**Step B — Classify each posting title** into one of three seniority bands relative to the candidate's resume:
- **Current-level** — lateral or peer role: same or similar seniority to the candidate's current title
- **Promotion-level** — one step up: natural next step. For a Senior Manager: Director, Head of, VP. For Staff Engineer: Principal or Distinguished.
- **Demotion/adjacent** — below current seniority, or on a different track. May still be relevant — just ranks lower.

**Named company** — posting type is `greenhouse`, `ashby`, `lever`, `bamboohr`, `teamtailor`, or `workday` (NOT `rss`).

**Before assigning T1/T2/T3**, split compatible postings into two pools:
- **`localPool`** — postings where `distanceMiles` is not null. `scan.mjs` pre-computes this by geocoding each unique non-remote job city and measuring haversine distance from `home_zip`. Any city within `local_radius_miles` of home gets a numeric `distanceMiles` value. If `home_zip` is not set, `distanceMiles` is always null and `localPool` is always empty.
- **`remotePool`** — all remaining compatible postings (anything where `distanceMiles` is null).

T1/T2/T3 tiering operates **only on `remotePool`**. Local postings never compete for remote-tier slots.

**Local pool sort:** Sort `localPool` by `distanceMiles` ascending (closest first). Within the same distance band (within 5 miles), sort current-level titles above promotion-level, then other. Relevance breaks ties within the same distance + title band.

Assign tiers from `remotePool` (mutually exclusive — once placed, exclude from lower tiers):
- **Tier 1** — named company AND (current-level OR promotion-level title). Sort: current-level first, then promotion-level; each group by relevance desc.
- **Tier 2** — named company AND any other relevant title (demotion, adjacent, or any match from `targets.roles`). Sort: current-level first, then promotion-level, then other; each group by relevance desc.
- **Tier 3** — any source (RSS or named), where relevance ≥ 3 OR title is current-level or promotion-level. Sort: current-level first, then promotion-level, then other; each group by relevance desc.

**Across all tiers, title proximity to the candidate's current position is the primary sort key.** Relevance score breaks ties within each title band.

**After tiering, do NOT write `data/session-pick-list.json` yet.** That file is written after pre-screening completes (step 5a).

### Step 4 — Show a relevance-ordered placeholder immediately

While pre-screening runs, output the pick list using relevance order so the user has something to read. Show top 5 per tier by relevance. Label it clearly as preliminary:

```
Scoring matches... (this takes ~30 sec)

 1. Vanta      — Head of Solutions Engineering, Americas     · Remote (US)
 2. GitLab     — Engineering Manager, Supply Chain Security  · Remote (US)
 3. Cloudflare — Senior Manager, Solutions Engineering       · Distributed
 4. Cloudflare — Senior Solutions Engineering Manager, West  · Distributed
 5. Instacart  — Senior Engineering Manager, Carrot Ads      · Remote (US)
 ...
```

Then immediately proceed to step 5a without waiting for user input.

**Location normalization:** Format location as a short label after `·`. Take only the first segment if multiple locations are listed (split on `;`). Normalize → "Remote (US)": "Remote, USA", "Remote, US", "United States - Remote", "US - Remote", "USA - Remote", "Remote- USA", "US (remote)", "USA (Remote)", "UNITED STATES - Remote". Normalize → "Remote (CA)": "Remote, Canada". Normalize → "Remote (UK)": "Remote, UK", "Remote, United Kingdom". Normalize → "Remote": bare "Remote" or "GLOBAL - Remote". Omit `·` if location is null.

**Local tier location labels:** For local pool entries, show the nearest city and distance. Find the city segment within `local_radius_miles` with the smallest `distanceMiles`. Format as `City (Nmi)` — e.g. `San Antonio (8mi)`. If `distanceMiles` ≥ 100, show only the city name.

Do not show any footnote about excluded or snoozed counts — the list is already filtered.

Note: Discarded tracker entries are suppressed for 60 days, then reappear. Snoozed (skipped) postings are suppressed for 30 days. All other tracker statuses (Applied, Evaluated, Interview, etc.) are suppressed indefinitely.

### Step 5 — Discover footnote

If discover added new companies during this run, show one quiet line:

```
Added 3 companies to your scan list: Acme Corp, BuildCo, Veriff.
```

If no new companies were added, omit this line entirely.

### Step 5a — Automatic pre-screen (two-phase light scoring)

Run immediately after step 4 — no prompt, no confirmation.

The goal is to score **every compatible posting** and surface the genuine best 5 per tier. Two fast phases replace a full JD evaluation.

---

**Phase 1 — Metadata score (instant, no fetches)**

Score every posting in all four pools (t1, t2, t3, localPool) using only data already in the cache:

| Signal | Weight | Notes |
|--------|--------|-------|
| Title seniority fit | 40% | current-level = 1.0, promotion-level = 0.85, adjacent = 0.5, demotion = 0.2 |
| Scanner relevance (normalized) | 35% | divide raw relevance by 10 to get 0–1 |
| Location compatibility | 15% | remote/distributed = 1.0, local within commute = 0.9, onsite out of range = 0.0 |
| Source quality | 10% | named ATS (greenhouse/ashby/lever/etc.) = 1.0, RSS = 0.7 |

Multiply weighted sum by 5 to get a 0–5 phase-1 score. Sort each tier by phase-1 score desc.

Take the **top 25 per tier** (top 25 from t1, top 25 from t2, top 25 from t3, top 25 from localPool) into phase 2. All remaining postings are kept in tier buffers scored by phase-1 score for later slot replacement.

---

**Phase 2 — JD summary fetch (parallel, ~25–100 fetches)**

Fetch the first **500 characters** of each phase-2 candidate's JD URL in parallel (up to 100 concurrent). Parse the visible text from whatever is returned — ignore HTML tags, navigation, headers. You only need the opening paragraph or summary section.

For each fetched posting, compute a **phase-2 keyword score**:
- Extract keywords from the 500-char snippet
- Compare against the candidate's skill keywords from `resume.md` (languages, frameworks, tools, domain terms)
- Score = (matching keywords / total keywords checked), normalized to 0–1
- Blend with phase-1 score: `final_score = (phase1 * 0.5) + (keyword_match * 5 * 0.5)`

If a JD URL is unreachable (404, timeout, empty), keep the phase-1 score as the final score and mark `fetched: false`.

---

**Slot selection per tier:**

After phase 2 completes, sort each tier's scored pool by final_score desc. Fill each tier's 5 display slots using this priority:
1. Score ≥ 4.0 — sorted by score desc
2. Score ≥ 3.0 — sorted by score desc (only if fewer than 5 slots filled)
3. Score ≥ 2.0 — sorted by score desc (only if fewer than 5 slots filled)
4. Unscored/unreachable — sorted by phase-1 score desc (last resort only)

Never show fewer than the available candidates (if a tier has only 3 postings total, show all 3).

---

**Re-present the final pick list**, replacing the placeholder from step 4. Use `✓` for score ≥ `targets.min_score` and `✗` for below. Sort within each tier group by score desc.

```
 1. ✓ 4.2  Vanta      — Head of Solutions Engineering, Americas    · Remote (US)
 2. ✓ 4.0  Instacart  — Senior Engineering Manager, Carrot Ads     · Remote (US)
 3. ✓ 3.8  GitLab     — Engineering Manager, Supply Chain Sec      · Remote (US)
 4. ✗ 2.9  Cloudflare — Senior Manager, Solutions Engineering      · Distributed
 5. ✗ 2.7  Cloudflare — Senior Solutions Engineering Manager, West · Distributed

 6. ✓ 4.1  Reddit     — Director of Engineering, Ads Measurement   · Remote (US)
...

Scores: 1–5 · ✓ = strong match (≥ 3.5) · ✗ = below threshold

Pick a number to evaluate fully, or multiple (e.g., "1, 3, 5").
Type "all top" to evaluate the top 5.
Type "skip" to finish.
```

**Write `data/session-pick-list.json`:**
- `cache_timestamp`: `scanTimestamp` from read-cache.mjs output
- `built_at`: current ISO timestamp
- `prescreened: true`
- `shown`: the 5 scored picks per tier, each with `{ slot, tier, url, company, title, location, score, fetched }`. Local entries use `tier: "local"`.
- `buffers.t1`: all remaining t1 candidates sorted by final_score desc (phase-1 score for unfetched)
- `buffers.t2`: all remaining t2 candidates sorted by final_score desc
- `buffers.t3`: all remaining t3 candidates sorted by final_score desc
- `buffers.local`: all remaining local candidates sorted by final_score desc

### Step 6 — User picks

When the user picks a number, look up the URL from the `shown` array in `data/session-pick-list.json` (or from the postings array if the session file wasn't written) and run the evaluate flow — no URL copy-pasting needed.

### Step 7 — After each evaluation

- If score ≥ `targets.min_score` (from profile.yml): automatically run the full tailor flow (resume + cover letter + PDFs) without asking — then open the job posting URL in the browser with `open <url>`, then ask: **"Did you apply? (y/n)"**
  - **y** → add to tracker.md with status `Applied`, include PDF links in the PDF column
  - **n** → add to tracker.md with status `Evaluated`, no PDF links; offer to pick another from the list
- If score < `targets.min_score`: add to tracker.md with status `Discarded`; offer to pick another from the list or stop.

**MANDATORY — slot replacement (do this before any user prompting):**
Every evaluate outcome (Applied, Evaluated, Discarded) must trigger a slot replacement.

1. Read `data/session-pick-list.json`
2. Remove the evaluated posting from `shown`
3. Renumber all remaining `shown` entries consecutively starting at slot 1
4. Pull the next candidate from the tier buffer matching the removed entry's `tier` field:
   - `tier: "t1"` → pull from `buffers.t1`; if empty, try `buffers.t2`; if still empty, `buffers.t3`
   - `tier: "t2"` → pull from `buffers.t2`; if empty, try `buffers.t3`
   - `tier: "t3"` → pull from `buffers.t3` only
   - `tier: "local"` → pull from `buffers.local` only (no cascade to remote tiers)
5. If all matching buffers are empty, do a lazy refill:
   a. Run `node scripts/read-cache.mjs --top 150`
   b. Filter out all URLs currently in `shown`
   c. Classify remaining postings into local/t1/t2/t3 using the same logic as step 3
   d. Populate `buffers.t1/t2/t3/local` with ALL newly classified candidates
   e. Write the updated session file
   f. Pull from the appropriate tier buffer
   If even after lazy refill no candidates exist, show the list with fewer than 20 entries (final fallback only).
6. Append the replacement at slot = (length of remaining shown + 1) — always goes at the bottom
7. Write the updated `data/session-pick-list.json`
8. Display the full refreshed pick list with `*` next to the new entry

Then offer to pick another from the list or stop.

### Step 8 — "All top"

If the user says "all top", evaluate the top 5 sequentially, showing a brief score summary after each.

### Step 9 — "Skip"

When the user types "skip" — snooze all postings from the current pick list that were NOT evaluated in this session:

- Collect URLs + company + title for every posting in the pick list (up to 20 entries) that the user did not pick for evaluation.
- Read `data/dismissed.json` (parse as array; treat as `[]` if missing or unreadable).
- For each unselected posting, upsert into the array using `url` as the dedup key:
  ```json
  {
    "url": "...",
    "company": "...",
    "title": "...",
    "shown_at": "<current ISO timestamp>",
    "hide_until": "<current ISO timestamp + 30 days>"
  }
  ```
  If the URL already exists, overwrite the entry (resets the 30-day window).
- Write the updated array back to `data/dismissed.json`.
- Delete `data/session-pick-list.json` (use Bash `rm -f`) so stale session state doesn't persist.
- Output exactly one quiet line:
  ```
  {N} postings snoozed for 30 days.
  ```
- Do NOT show this snooze line if every posting in the pick list was evaluated (nothing left to snooze).
